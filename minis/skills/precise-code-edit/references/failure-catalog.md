# 事故档案：为什么要这么麻烦

每条都来自真实项目（MIDI8BIT 单文件 Web 播放器，约 2000 行、75 个顶层函数），
每一条都真实发生过，且都是"看不出来"的那种。

## 1. 删了函数，忘了删导出表的引用 → 整个导出变 undefined

删掉不再需要的 `trimIDB()` 后，文件末尾仍有：
```js
window.MIDI8 = { ..., trimIDB, ... };
```
结果：赋值时抛 `ReferenceError`，`window.MIDI8` 是 `undefined`。
**页面完全正常**（播放列表、渲染、UI 全在跑），`node --check` 通过，
只有主动查 `typeof window.MIDI8` 才暴露。
→ 规则 L1；`verify_edit.py --exports` 就是为这条写的（已在复刻夹具上验证能抓到）。

## 2. 手工切片删代码，切多一行留下残骸 → 整页白屏

用 `find(起点)` + `indexOf('});')` 切掉一个 UI 选择器块，切多了，留下 5 行孤零代码：
语法错误 → 白屏。肉眼 diff 时那 5 行"看着像注释区"。
→ 规则：区域替换必须交给脚本并断言锚点唯一；改完立刻 L0。

## 3. 切少一行 → 静默什么都没改，却报告"已修复"

同一根因的另一半：锚点写错一个字符，`replace` 匹配 0 次，**不报错、不改变**，
于是"修好了"的结论建立在空改动上。
→ 规则 5：0 次命中必须报错。

## 4. no-op 修复：改了，但行为一模一样

把 `let us = 500000;` 改成 `let us = tempos.length ? tempos[0].us : 500000;` ——
而 `tempos` 数组索引 0 永远是一个占位符、长度恒 ≥ 1，两种写法行为完全相同。
**改动的字面看起来更"正确"，实际什么都没变。**
更糟的是验证："实测 170 / 142" —— 这两个值改前就存在（循环本来就会取到真实事件），
作者拿想象中的"修前值"对比，等于自欺。
→ 规则 6 + 举证责任："必须实测改动前的值"。

## 5. 验证脚本自己的锚点不存在 → 误报"改动没落地"

一次性检查脚本里写 `T.indexOf('async function loadFromUrl')`，
而实际声明是 `function loadFromUrl`（非 async）→ 返回 `-1` → 切片为空 →
脚本报告"目标代码里没有这段"。差点据此重做一遍已经正确的改动。
→ 使用任何基于字符串定位的验证前，先断言锚点存在。

## 6. 同名变量的替换误伤

清理死字段时按名字全量替换 `peak`，但 `peak` 这个名字还被用于
`toneHit/noiseHit` 的形参、以及示波器峰值表 —— 8 处命中里只有一部分该删。
→ 规则 2：锚点要带上下文；大批量替换后必须逐处复核 `--count` 报告的数量。

## 7. 字节记账口径漏项（"多写"的反面）

缓存大小记账只算 PCM（`frames*nch*2`），漏了音轨缩略图（`+ sw*2`）：
短曲少记 12.5%，30 分钟单声道曲少记 25% → 淘汰逻辑阈值失真。
→ 规则 7：改动前后逐项复算不变量。

## 8. 分析工具自己的解析层有 bug：`--unused` 把 128/168 个标识符报成"死代码"

`verify_edit.py --unused` 在真实项目（`index.html`，3212 行）上报告
**168 个顶层标识符里 128 个"未被使用"** —— 包括 `startRender`（实际 15 处）、
`storeMaster`（10 处）、`kickRender`、`updateInfo` 这类到处引用的函数。
先前的"零死代码"结论因此不能采信这一项。

**根因**（用"最长空白段"定位，不是靠猜）：
`strip_strings_and_comments()` 不识别正则字面量。文件里有一行

```js
const esc = s => String(s).replace(/[&<>"]/g, c => ({"&":"&amp;"}[c]));
```

其中的 `"` 被当成字符串开头，剥离器一路吞掉 **61762 字节**（占整个脚本的近一半），
被吞区域里的标识符自然"只出现一次"。修复后 `strip_ratio` 从 **0.184 → 0.599**，
误报从 128 条降到 0 条。

**更危险的是反方向**：同样这 62KB 被吞掉，意味着如果里面有悬空引用，
`--exports` 会**静默漏报**。本文件上两次结论恰好都是 `{}`（侥幸），
但那是运气，不是正确性。

**教训**：
1. **工具的解析层和被测代码一样会错，而且它错的时候不报错。**
   凡是分析类脚本，都必须输出一个能被外部检验的健全性指标
   （这里是 `strip_ratio`：剥离后非空白占比），并在异常时自己报警 —— 已加为
   `stripper-suspicious` 金丝雀（阈值 0.15）。
2. **定位方法**：不要猜"哪里出错了"，直接找"输出里最长的空白段"并打印原文上下文
   —— 失控的剥离器一定表现为一段超长空白。这次一次命中。
3. **同一个分析层同时供给多个结论时，一个 bug 会污染所有结论**（`--exports`、
   `--unused` 共用剥离器）。修完要**逐个结论重测**，不能只测报错最明显的那个。



| 事故 | 形态 | 抓它的是哪一级 |
|---|---|---|
| 1 | 多删引用 | L1 悬空引用 |
| 2 | 多切一行 | L0 语法 |
| 3 | 少切一行 | 替换计数断言 |
| 4 | 改了等于没改 | no-op 检测 + 实测改动前的值 |
| 5 | 验证工具自身失效 | 锚点存在性断言 |
| 6 | 替换误伤同名 | 锚点唯一性 + 逐处复核 |
| 7 | 口径漏项 | 不变量逐项复算 |
| 8 | 分析工具自身解析错 | 健全性金丝雀（strip_ratio）|

**规律：代码改动的错误几乎都不是"逻辑想错了"，而是"机械动作没对账"。**
所以解法也不是"更小心"，而是**把每一次机械动作都变成一条可断言的数字** ——
包括"检查工具的检查结果"这件事本身。
